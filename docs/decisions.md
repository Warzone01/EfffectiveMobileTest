# Архитектурные решения (ADR-lite)

## D-001. Многомодульная структура

- Статус: принято.
- Решение: разделить проект на `core`, `domain`, `data`, `feature`, `app`.
- Почему:
  - ТЗ требует многомодульность;
  - быстрее сборка и изолированные изменения;
  - проще поддерживать границы ответственности.

## D-002. Pattern: Clean Architecture + MVVM

- Статус: принято.
- Решение: use-case в domain, repository abstraction, UI на MVVM.
- Почему:
  - соответствует ТЗ;
  - изолирует бизнес-логику;
  - упрощает тестирование.

## D-003. UI state модель: Event/State/Effect

- Статус: принято.
- Решение: в каждой фиче использовать `UiEvent`, `UiState`, `UiEffect`.
- Почему:
  - предсказуемые переходы состояния;
  - отделение одноразовых действий (навигация, сообщения) от состояния экрана.

## D-004. Сетевой слой на Retrofit

- Статус: принято (обязательное требование ТЗ).
- Решение: `Retrofit + OkHttp`, отдельный `CoursesApi`, mapper DTO -> domain.
- Почему:
  - выполнение прямого требования ТЗ;
  - простая интеграция и тестируемость.

## D-005. Локальное хранение избранного через Room

- Статус: принято.
- Решение: хранить только отметки избранного (`courseId`) в отдельной таблице Room.
- Почему:
  - ТЗ требует локальную запись избранного;
  - минимальный объем локальных данных;
  - нет необходимости дублировать весь ответ API.

## D-006. Политика объединения API и local favorites

- Статус: принято.
- Решение: итоговое значение `hasLike` рассчитывать как `api.hasLike OR localFavoriteExists`.
- Почему:
  - сохраняет серверную и локальную избранность;
  - обеспечивает ожидаемое поведение при повторной загрузке списка.

## D-007. Сортировка publishDate

- Статус: принято.
- Решение: сортировать в domain use-case по убыванию `publishDate`.
- Почему:
  - бизнес-правило должно быть вне UI;
  - сортировка переиспользуется в `home`/`favorites` при необходимости.

## D-008. Навигация через feature API + core navigation contracts

- Статус: принято.
- Решение: каждая фича имеет `api`-модуль с контрактом экрана, `app` собирает bottom nav.
- Почему:
  - минимизирует связанность между фичами;
  - упрощает замену/перенос реализации экрана.

## D-009. Обработка ошибок

- Статус: принято.
- Решение: единый `AppError` + маппинг исключений на data слое.
- Почему:
  - единообразное поведение UI;
  - отсутствие raw exceptions в presentation.

## D-010. Валидация входа

- Статус: принято.
- Решение:
  - email проверяется на формат `text@text.text` и запрет кириллицы;
  - кнопка входа активна только при валидном email и непустом пароле.
- Почему:
  - прямое соответствие ТЗ;
  - уменьшение количества невалидных переходов.

## D-011. Non-functional элементы главного экрана

- Статус: принято.
- Решение: поиск и иконка фильтра отображаются как статичные элементы UI.
- Почему:
  - ТЗ явно указывает нефункциональность этих элементов.

## D-012. AdapterDelegates для списка курсов

- Статус: принято.
- Решение: список курсов строится через AdapterDelegates.
- Почему:
  - соответствует рекомендуемому стеку;
  - удобен для расширения карточек и placeholder-состояний.
